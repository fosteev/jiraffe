# Jiraffe MVP — на подтверждение

## Решения на подтверждение

- [скоуп] этап 1: `parseDuration` отвергает ноль (`0`, `0м`), ввод меньше полуминуты и больше 10 000 ч (→ `null`), голое число — часы только если это весь ввод (`1 30` → `null`); результат округляется до целых минут — логировать ноль/секунды/опечатку в 10⁶ ч бессмысленно, Jira и так считает в минутах — откат: правка двух условий в `src/duration.ts` + тесты
- [архитектура] этап 1: тулчейн — vitest 3 (не 5: тот требует @types/node ≥22), TypeScript 6, ESLint 10, vsce 4 (требует Node ≥22 для разработки), `@types/vscode` запинен 1.90.0; один tsconfig на хост и webview (lib ES2022+DOM) — latest на момент сборки и совместимость с @types/node@20 — откат: смена версий в package.json + `npm i`; tsconfig разнести на два при конфликте DOM-типов (этап 4)
- [архитектура] этап 2: `id` инстанса = slug `host+path` (`atlassian-tatikoma-ru-jira`); он же ключ токена `jiraffe.token.<id>` в SecretStorage — два аккаунта на одном хосте (и http/https одного хоста) завести нельзя, повторное добавление предлагает «Заменить» — в MVP по одной учётке на инстанс — откат: id = slug + суффикс (`-2`) или uuid, миграция ключей globalState/SecretStorage
- [архитектура] этап 2: «Tempo нет» = 404 **или** 200 с HTML вместо JSON (sccloud/tatikoma отвечают 302 на `login.jsp`, fetch идёт по редиректу); 401/403/сеть пробрасываются — так ответил живой сервер, 404 там не бывает — откат: условие в `src/jira/capabilities.ts`; риск — DC с Tempo за SSO-прокси, отдающим HTML, будет считаться «без Tempo» (лечится «Обновить возможности» после починки прокси)
- [скоуп] этап 2: на Cloud Tempo не определяется вовсе (`tempo=false` без запроса) — Tempo Cloud живёт в отдельном API `api.tempo.io` со своим токеном, в MVP не поддерживается; на Cloud время логается стандартным worklog — откат: ветка `kind === 'dc'` в `detectCapabilities` + отдельный TempoCloudClient (после MVP)
- [архитектура] этап 2: контракт эпика — DC: поле Epic Link (`instance.epicLinkField ?? caps.epicLinkField`, JQL `cf[<id>] = KEY`), Cloud: `fields.parent` с `issuetype.hierarchyLevel === 1`, JQL `parent = KEY`; на Cloud `/field` за Epic Link не ходим (Atlassian перевёл и company-managed проекты на `parent`) — выбор по `instance.kind`, а не по наличию поля, задевает этапы 4 и 7 — откат: поле `Capabilities.epicMode: 'field' | 'parent'` и детект `customfield_10014` для старых Cloud-сайтов
- [архитектура] этап 2: редиректы — `fetch` по умолчанию (`follow`), undici сам снимает `Authorization` на чужом origin; после ответа смена origin → `JiraError code:'redirect'` («укажите этот адрес»), `manual` отвергнут (ломает признак «Tempo нет» через `login.jsp`) — все будущие методы HttpClient (бинарный GET, POST) обязаны повторять проверку — откат: `redirect: 'manual'` + явная обработка 3xx в `getJson` и `detectCapabilities`
- [скоуп] этап 2: `Instance.epicLinkField` (ручное переопределение Epic Link из плана) UI не получил — редактирования инстанса в плане нет; потребители берут `instance.epicLinkField ?? instance.caps?.epicLinkField` — откат: команда «Изменить инстанс» (поле Epic Link) в этапе 8
- [скоуп] этап 3: корневые узлы «Задач» во всех режимах — инстансы (`имя · host · N`), а в прототипе режим JQL — плоский список «Найдено: N», режим «проект» — заголовок группы `KEY · инстанс · N` — счётчик, ошибка и «Загрузить ещё» живут у каждого инстанса отдельно, плоский список из нескольких инстансов требует слияния страниц по `updated` — откат: в `IssuesTree.getChildren` при одном опрашиваемом инстансе отдавать задачи прямо в корень (заголовок — в `TreeView.message`)
- [скоуп] этап 3: «Готово» в быстром фильтре в режиме «на мне» снимает `resolution = Unresolved` (иначе выдача всегда пустая); остальные категории его оставляют — откат: строка в `buildJql` (`jql.ts`)
- [скоуп] этап 3: поиск `ABC-123` даёт `(key = ABC-123 OR text ~ "ABC-123")` — сама задача плюс упоминания; ключом ищется только на инстансах, где есть проект `ABC`, иначе (и для `UTF-8`, `ISO-9001`) — только текстом; на DC «задачи с таким ключом нет» (400) — повтор текстом. Плюс строка «Открыть … по ключу», как в прототипе — по плану было голое `key = …`: оно не находило `UTF-8` и давало 400 на чужих DC — откат: `textAsKey` в `buildJql` и ветка 400 в `IssuesTree.load`
- [скоуп] этап 3: в поиске экранируются операторы Lucene, `*`/`?` остаются подстановками, `AND/OR/NOT` — как слова: синтаксис Lucene (`-слово`, `поле:значение`) из строки поиска недоступен, для него — «Редактировать JQL» — откат: `luceneEscape` в `jql.ts`
- [скоуп] этап 3: «Редактировать JQL» из режимов «на мне»/«проект» запекает в JQL только режим и категории статуса; типы, приоритеты, поиск и выбор инстансов остаются быстрыми фильтрами поверх (запечённый тип, которого нет на инстансе, даёт 400) — откат: `editJql` в `commands/filters.ts` (`baked: 'all'`)
- [скоуп] этап 3: проект, локальный фильтр с привязкой и избранный фильтр Jira опрашивают только свой инстанс; JQL, введённый руками, — все выбранные. Выбранные типы/приоритеты сужаются до существующих на инстансе; если там нет ни одного — инстанс не опрашивается (пусто) — откат: `activeInstanceIds` (`state/filters.ts`), `jqlForInstance` (`state/query.ts`)
- [архитектура] этап 3: категории статуса в JQL — по id (`new` = 1,2; `indeterminate` = 4; `done` = 3), не по локализованным именам; инвариант «сумма = проект» в smoke — откат: имена категорий в `CATEGORY_IDS` (`jql.ts`)
- [архитектура] этап 3: состояние фильтров в `globalState` — `jiraffe.filterState` (режим, проект `{instanceId,key}`, JQL, привязка, быстрые, текст, инстансы) и `jiraffe.filters` (локальные фильтры с необязательным `instanceId`); битое отбрасывается при чтении, версии формата нет — смена формата потребует миграции — откат: ключ с версией (`jiraffe.filterState.v2`) и чтение старого
- [архитектура] этап 3: модули вне «Архитектуры» — `src/commands/filters.ts`, `src/state/meta.ts` (`InstanceMeta`: общий кэш проектов/типов/приоритетов и фабрика клиента для этапов 4 и 7), `src/state/query.ts`, `src/views/format.ts`; `jiraffe.refresh` живёт в `registerFilterCommands` — откат: перенос функций, контракт команд не меняется
- [архитектура] этап 4: протокол host↔webview карточки (`src/panels/protocol.ts`) — состояние (данные, вкладка, закреплённость) живёт в хосте, webview при каждой загрузке шлёт `ready` и получает его заново (`retainContextWhenHidden: false`, повторного GET при показе вкладки нет); действия карточки хост исполняет командами `jiraffe.logWork(IssueRef)` / `jiraffe.openEpic({instanceId,key})` / `jiraffe.openRelease({instanceId,id})`, этапы 6–7 меняют только их тела; ключи и id из webview проверяются по формату (`isIssueKey`/`isVersionId`), действия над задачей несут её `key` (устаревший вид игнорируется), ссылки — только http/https/mailto (`safeExternalUrl`) — откат: перенести обработчики в `IssuePanelManager.onMessage`, хранить состояние в webview (`retainContextWhenHidden: true` — дороже по памяти)
- [архитектура] этап 4: санитизация в хосте через `sanitize-html` (новая runtime-зависимость, вшита в `dist/extension.js`), белый список шире плана (`b/i/u/s/del/ins/sub/sup/hr`, части таблиц, `tt`→`code`), все `class` Jira вычищаются; `img` → `<span class="img-ph" data-src>` — контракт этапа 5: `data-src` ставит только этот трансформ и только для картинок своего инстанса (origin + context path), чужие http(s)-картинки — ссылкой «[внешняя картинка]», такие же span из самого HTML Jira обезвреживаются — откат: другой санитайзер/список в `src/jira/sanitize.ts`; контракт `.img-ph[data-src]` трогает этап 5
- [архитектура] этап 4: CSP без `unsafe-inline` для стилей — в разметке нет `style=`, цвет аватара и ширина полосок ставятся из `issue.ts` через CSSOM по `data-bg`/`data-w`; разметка карточки — чистые функции `webview/render.ts` (строки HTML, всё из Jira через `esc`, кроме санитизированных описания/комментариев) — откат: шаблонизатор/DOM-сборка в webview; ослаблять CSP не план
- [скоуп] этап 4: аватары — инициалы с цветом по хэшу, иконки типа и приоритета — свои SVG по названию (en/ru эвристика), а не картинки с инстанса (CSP не пускает чужие хосты, а авторизованное скачивание — этап 5) — откат: после этапа 5 качать `avatarUrls`/`iconUrl` как `data:` тем же механизмом
- [скоуп] этап 4: плашка статуса — 3 цвета по `statusCategory` (Открыта/В работе/Готово) с названием статуса из Jira; 4-й «Ревью» из прототипа нет (в Jira такой категории нет) — откат: карта «название статуса → цвет» в `webview/render.ts`
- [скоуп] этап 4: «Релиз» в мета-колонке — все `fixVersions` ссылками (в прототипе одна); крошка показывает ключ эпика, строка «Эпик» — его название — откат: `renderMeta`/`renderCard` в `webview/render.ts`
- [скоуп] этап 4: картинки с чужих хостов в описании/комментариях — сразу ссылкой «[внешняя картинка]» (этап 5 их и не покажет: CSP и запрет слать токен наружу), картинки своего инстанса — плейсхолдер до этапа 5 — откат: трансформ `img` в `src/jira/sanitize.ts`
- [скоуп] этап 4: история и журнал работ — без догрузки страниц: changelog — сколько отдал `expand=changelog` (до 100 записей), worklog — один `GET /worklog` (DC отдаёт все, Cloud — до 5000); у задач с длинной историей старые записи не видны — откат: пагинация `/changelog` и `/worklog?startAt=` в `JiraClient`
- [скоуп] этап 4: карточки не восстанавливаются после перезапуска VS Code (serializer не зарегистрирован); повторное открытие закреплённой задачи перечитывает её с сервера; новая задача в preview открывается на «Описании» — откат: `registerWebviewPanelSerializer('jiraffe.issue')` с `{instanceId,key,pinned}` в state
- [архитектура] этап 5: бинарный GET (`HttpClient.getBinary`) ведёт редиректы сам (`redirect: 'manual'`, до 5): `Authorization` — только адресам инстанса (origin + context path) и только пока цепочка не покидала инстанс; на чужой origin — только https и без кредов (Cloud → media-хост с подписанной ссылкой), на чужой http — отказ, на `login.jsp` — 401. Отличается от решения этапа 2 (`follow` в `getJson`) — POST этапа 6 должен повторить ту же модель — откат: `redirect: 'follow'` + проверка `res.url` как в `getJson` (теряется Cloud-редирект без токена и явный 401 вместо HTML)
- [архитектура] этап 5: webview не знает адресов Jira — карточка уходит без `contentUrl/thumbnailUrl`, картинки описания — `span.img-ph[data-img="iN"]`, вложения — `tID`/`fID`; адреса живут в хосте (`LoadedCard {card, files, inlineUrls}`), картинки приходят по одной `attachmentPreview {instanceId, key, id, dataUri|error}`, тип — по сигнатуре (SVG пускается только как `data:` в `<img>`), кэш — LRU ~64 МБ в памяти хоста, ≤3 скачивания одновременно — откат: передавать URL в webview нельзя (CSP/токен); менять можно размер кэша/параллелизм константами в `src/panels/attachments.ts`
- [скоуп] этап 5: лимиты — превью/картинки описания/лайтбокс до `jiraffe.maxImageMb` (по умолчанию 5, 1..50; больше — «скачайте файл»; картинка больше 50 Мпикс или SVG больше 1 МБ тоже не показывается — защита от decompression bomb), «Скачать» — потолок 200 МБ (не больше 2 сохранений одновременно) (файл держится в памяти), «Открыть в редакторе» — 50 МБ, константами без настройки — откат: `MAX_DOWNLOAD_BYTES`/`MAX_TEXT_OPEN_BYTES` в `src/jira/attachments.ts` или потоковая запись на диск для больших файлов
- [скоуп] этап 5: в `.jiraffe/` при первом сохранении пишется `.gitignore` с `*` (только для пути по умолчанию и если файла нет) — чтобы вложения не попали в git пользователя — откат: убрать запись в `AttachmentService.root()`
- [скоуп] этап 5: `jiraffe.attachmentsDir` — абсолютный путь принимается только из пользовательских настроек; из настроек workspace абсолютный или выходящий за папку (в т.ч. через каталог-симлинк) путь игнорируется → `.jiraffe` + предупреждение; без открытой папки — `<tmp>/jiraffe`, папки задач там удаляются через 7 дней при активации — откат: `resolveAttachmentsRoot` и `cleanupTmp`
- [скоуп] этап 5: имя файла на диске — санитизированное имя из Jira: без каталогов, ведущих точек (dotfiles не создаются: `.env` → `env`), управляющих/bidi символов, `<>:"|?*` и «похожих на слэш» → `_`, ≤180 байт; дубли имён в задаче (`image.png` ×N) — ` (id)` перед расширением — откат: `safeFileName`/`attachmentFileNames`
- [скоуп] этап 5: «Открыть в редакторе» показывается по расширению (txt log json xml csv tsv md yaml yml ini conf cfg properties sql diff patch har) или текстовому mime из метаданных Jira, сохраняет файл в `.jiraffe/<KEY>/` (как «Скачать») и открывает его, только если в первых 64 КБ нет NUL; внешними программами ничего не открывается (только «Показать в папке») — откат: `isTextAttachment`/`openInEditor`
- [скоуп] этап 5: картинки описания и комментариев кликабельны — открываются в том же лайтбоксе, что и вложения (в прототипе — только вложения), даже если Jira обернула картинку в ссылку — откат: `img[data-zoom]` в `webview/issue.ts`
